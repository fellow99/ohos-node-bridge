## 1. 模块概述

### 1.1 目的

在**宿主应用进程内**让 Node 运行时跑起来，且：

1. 加载与启动动作**不占 UI 线程**；
2. 平台对运行时的系统调用限制被就地化解或如实记录；
3. 平台不支持的运行时行为**不被静默吞掉**——失败必须留下可读证据（原则 C2 / C6）。

模块交付物是一个随 HAP 编译的原生引导件（`libnode_bridge.so`），对上只开 3 个能力入口（规约 S8）。

### 1.2 解决的问题

| 问题 | 现象 | 本模块的处置 |
|---|---|---|
| 平台封死子进程 / 独立可执行 | 只能进程内运行（规划 §4.4 / §4.6 路线 A） | 进程内加载运行时并调用其入口 |
| 在 UI 线程启动会 ANR | `APP_INPUT_BLOCK`，先例旧版本被系统杀（规划 §5.10 ①） | 专用执行线程 + 分离语义 + 32 MB 栈 |
| 运行时初始化被系统调用限制打断 | libuv 初始化即崩（规划 附录 B #4） | 系统调用拦截（返回**正好 -1**）+ 环境变量双保险 |
| 参数个数算错即段错误 | `node::Start` 5 ms 内 SIGSEGV（规划 附录 B #3） | 固定 argv 构造 + 哨兵约束 + 逐条打印自检 |
| 崩溃后无法自动恢复 | 进程内不可重启（规划 §5.2 / 硬约束 ⑥） | 一次性启动 + 崩溃取证（当前文本、Phase 1 结构化） |

### 1.3 范围

| 类别 | 内容 |
|---|---|
| **含（本模块）** | 入参封送与缺省值装配；独立执行线程（栈容量、分离语义）；单次加载约束的引导件侧兜底；运行时库有序定位链；入口符号解析；平台系统调用拦截；环境注入；启动前置探针；启动参数（argv/argc）构造；标准输出/错误重定向与缓冲策略；健康探针标志；崩溃信号取证；日志双通道与其信号安全性；构建产物落点；构建期链接面最小化；上述各项的失败可见性 |
| **不含** | ArkTS 侧状态机 / 单例 / 选项装配（`001-runtime-core`）· 载荷解包与入口解析（`004-payload-bootstrap`）· 宿主能力桥（`003-host-bridge`）· 日志环 / 崩溃记录读回 / `/facts`（`006-observability`）· 运行时获取、ELF 门禁与投放（`005-provision-verify`）· HAR 打包形态与许可清单（`007-distribution`）· 渲染、端口、探活策略（消费方） |

**边界判据**（原则 C1）：本模块只回答「运行时在本进程内怎么被加载与启动」；任何窗口、页面、端口、应用变量语义、鉴权都**不在**此模块。

## 4. 关键实体

### 4.1 引导上下文 `bridge_ctx`（一次性入参副本）

| 字段 | 容量 | 来源（as-built，`node_bridge.c`） | 关键属性 |
|---|---|---|---|
| `lib_dir` | 512 B | `start` 第 1 实参；上游传 `context.bundleCodeDir` | 用于拼 3 个绝对候选路径；空值 ⇒ 候选链只剩裸名 |
| `script` | 512 B | `start` 第 2 实参（`options.scriptPath`） | 作为 argv 最后一项；超 511 B 静默截断（FR-002-003） |
| `flags` | 256 B | `start` 第 3 实参；空 ⇒ `--no-verify-heap` | 空格分词；>10 个 token 静默丢弃；不做引号/转义解析 |
| `home` | 512 B | `start` 第 4 实参（`context.filesDir`） | 注入 `HOME`/`USERPROFILE` |
| `tmp` | 512 B | 派生 `home + "/tmp"` | 注入 `TMPDIR`/`TMP`/`TEMP`；创建目录（返回值未检查） |
| `log` | 512 B | `start` 第 5 实参（`Env.logPath`） | 复制进 `g_log_path`；标准输出/错误重定向目标 |

### 4.2 全局状态

| 名字 | 类型 | 含义 / 关键属性 |
|---|---|---|
| `g_log_path` | `char[512]` | 日志文件路径；投递失败时被清空 ⇒ 之后文件日志通道整体失效（D7 的一部分） |
| `g_node_running` | `volatile int` | 健康探针：进入运行时入口前置 1、返回后置 0 |
| `g_ctx` | 静态 `bridge_ctx` | **进程级单份**；调用线程写、引导线程读，**无同步**（D1） |
| `argbuf` | `static char[12][512]` | argv 各项的实际存储（约 6 KB，`.bss`） |
| `argv0` | `static char[] = "node"` | `argv[0]` 常量 |
| 候选链缓冲 | `char[4][640]`（栈上） | 运行时库的 4 个候选路径字符串 |

### 4.3 信号集与处置

| 信号 | 处置 | 关键属性 |
|---|---|---|
| `SIGSYS` | 系统调用拦截器 | `SA_SIGINFO \| SA_NODEFER`；按指令编码判命中；命中则返回 `-1` 并跳过该指令；**不**重新投递 |
| `SIGSEGV` / `SIGILL` / `SIGBUS` / `SIGABRT` / `SIGFPE` / `SIGTRAP` | 崩溃取证 | `SA_SIGINFO \| SA_RESETHAND`；写 `CRASH …` 后恢复默认处置并 `raise` 同一信号 |

### 4.4 常量

`MAX_ARGS = 12` · `CTX_PATH_LEN = LOG_PATH_LEN = 512` · 候选路径 640 B · 普通日志行缓冲 1024 B · 崩溃记录缓冲 512 B · 执行线程栈 `32 MiB` · 候选数 4 · 探针入参 `8` · 被 trap 的调用号 `425` · 目标指令编码 `0xd4000001` · 系统日志域 `0xD0033` / 标签 `NODE_BRIDGE`（**必须**与 `Logger.ets` 的 `DOMAIN` 相同，见 A1/R2）· 版本串 `node_bridge/0.2.0 (ohos-node-bridge Phase 1)`。

## 5. 验收场景

### 5.1 缺运行时库 ⇒ 可见失败（FR-002-010 / FR-002-027）

- **Given** 宿主沙箱内没有投放运行时库（`provision` 未执行），**When** 调用投递启动，**Then**：日志文件中出现 4 条候选尝试记录（含失败原因）与 1 条 `FATAL: 无法加载 libnode.so`；投递调用本身仍返回「已投递」；上游能据日志判定失败阶段。
- **预期（Phase 1 后）**：上游无需读日志即可拿到带阶段的结构化失败原因（§5.5 ③）。

### 5.2 符号缺失 ⇒ 可见失败（FR-002-011）

- **Given** 运行时库能被加载但**不含**入口符号，**When** 投递启动，**Then** 日志出现 `dlsym(node::Start) -> 0x0` 与 `FATAL: dlsym 失败: <原因文本>` 两次记录；健康探针保持 0（因为没有进入入口）。

### 5.3 启动参数构造正确（FR-002-017）

- **Given** 参数字符串为 `--no-verify-heap --expose-internals`、入口脚本为绝对路径，**When** 投递启动，**Then** 日志逐条打印 `argv[0]=node`、`argv[1]=--no-verify-heap`、`argv[2]=--expose-internals`、`argv[3]=<脚本绝对路径>`，且打印的参数个数为 `4`（**不含**尾部空指针哨兵）；运行时进入入口后 5 ms 内**不得**出现段错误（附录 B #3 的反例）。

### 5.4 UI 线程不被阻塞（FR-002-006 / FR-002-007 / FR-002-008）

- **Given** 应用在 ArkTS 主线程调用投递启动，**When** 运行时库有 120.9 MiB 且首次加载需要时间，**Then** 投递调用在毫秒级返回；`hilog` 中无 `APP_INPUT_BLOCK`；应用无 ANR；界面仍可响应用户操作。

### 5.5 崩溃留下结构化证据（FR-002-021 / FR-002-022）

- **Given** 运行时或载荷触发 6 个致命信号之一，**When** 进程崩溃，**Then** 日志文件中出现一条 `CRASH sig=… si_addr=… pc=… lr=… sp=… r0=…` 完整记录（7 项齐全），且系统侧仍按默认处置终止进程（**不是**被吞掉后继续跑）。
- **⬜ Phase 1 判据（升级本场景）**：除上述文本外，`<filesDir>/node-bridge/last-crash.json` 存在且可被 JSON 解析，字段含 `at / stage / signal / name / si_addr / pc / lr / sp / r0 / tid / logTail`；写入过程只用裸 `open`/`write`（S5 可静态检查）；下次启动时 `006-observability` 的 `lastCrash()` 能读回（规划 §5.7）。

### 5.6 重复启动被拒（FR-002-009）

- **Given** 第一次投递已进入执行线程，**When** 第二次调用投递启动（绕过上游单例，例如直接调用引导件入口），**Then** 第二次调用**不**覆写第一次的入参副本、**不**再创建执行线程、返回「已被拒绝」并保留首次失败原因。
- **⬜ 当前不满足**（D1：引导件无兜底，第二次调用会 `memset` 掉正在被使用的上下文）—— 本场景是 Phase 1 的验收门槛。

### 5.7 平台拦截未触发时的防御保留（FR-002-012 / FR-002-016）

- **Given** 基线设备（`HAD-W32 / HarmonyOS 6.1.0 / API 26 / arm64-v8a`）实测目标系统调用**返回正数**（无 seccomp trap，规划 §D.8），**When** 启动，**Then**：日志记录 `io_uring_setup(425) -> 8 (errno=0)`，拦截器**不被触发**且**不得**因此被删除（保留为跨机型防御）；相反，在会 trap 的设备上拦截器必须命中并让调用方看到失败。
- **⬜ 未闭环**：本机没有观测到拦截器命中一次 ⇒ 「命中路径」证据等级为 🔶 沿用（plan.md §7 给出可证伪的补测判据）。

### 5.8 边界与非法入参（FR-002-003 / FR-002-005 / FR-002-017）

- **Given** 下列任一输入，**When** 投递启动，**Then** 结果必须可见且不误导：
  1. 未传任何实参 / 入口脚本为空 ⇒ **拒绝**且不消耗唯一启动机会（⬜ Phase 1）；
  2. 实参类型不是字符串 ⇒ **拒绝**或明确告警（⬜ Phase 1）；
  3. 参数字符串超 255 B、入口脚本超 511 B ⇒ 出现截断告警（⬜ Phase 1）；
  4. 参数字符串含 12 个 token ⇒ 超出上限的 token 被丢弃且**必须**出现丢弃告警（⬜ Phase 1）；
  5. 日志目录不存在 ⇒ 出现「日志通道不可用」的可见降级信号（⬜ Phase 1）。

## 7. 假设与约束

1. **硬约束 ①**（规划 §4.2）：进程内加载运行时并调用其入口是**唯一可行**形态（子进程与独立可执行被平台封死，附录 B #16 / §4.6 路线 C）⇒ 本模块的全部设计以此为前提。
2. **硬约束 ②**（规划 §4.2 / §5.10 ①）：加载与启动必须在**非 UI 线程**完成，否则 `APP_INPUT_BLOCK`。
3. **硬约束 ③**（规划 §4.2 / §5.10 ③④）：被 trap 的平台调用必须返回**正好 `-1`**；环境变量（关闭 io_uring 探测）**不能**当唯一手段（部分构建里该变量被优化掉）。
4. **硬约束 ⑤**（规划 §4.2）：内部模块可见性靠「启动参数 + 纯 JS 桩」取得，零原生移植 ⇒ **启动参数的默认值属于本模块的对外行为**。**已定案（偏差已记录，不再是未解冲突）**：库默认 `flags = '--no-verify-heap'`（`NodeRuntime.ets`、`js_start()` 双层兜底），因为这是**真机验证过的**参数值且属最小可用集；`--expose-internals` **只在载荷走 internal-module stub 路线时才必需**（缺它 `internal/modules/*` 全 `MODULE_NOT_FOUND`），由消费方经 `flags`/`execArgv` 显式传入（规划 §5.3 草案的默认值已由本行取代；见 001 plan §3.5 / §9 第 8 条）。
5. **硬约束 ⑥**（规划 §5.2 / C5）：运行时入口每进程只能调用一次；崩溃是终态；本模块只能提供「拒第二次 + 留证据」，**不**提供恢复。
6. **⑰/⑱ 的落点**（规划 §D.10）：⑰（随机端口 + 单实例）与 ⑱（载荷自装异常兜底 + 写自己的日志）**主体在载荷/消费方**；本模块承担其中两条：**日志通道分离**（⑱ 指出的「日志重定向会把宿主渲染组件的原生输出一起写进日志文件」）与**崩溃取证可读**（⑰ 事故的根因判定依据）。
7. **设备差异必须被如实记录**：基线设备 `io_uring_setup(425)` 返回 **8**（无 trap）而 `harmonyos-node-notes` 的设备返回 `-1` ⇒ 拦截器的命中路径在本工程属 ⬜/🔶，不得当作已实测（规划 §D.8 / 证据纪律 1）。
8. **版本与 ABI 绑定面最小**：只依赖运行时的 ELF 属性与入口符号名（C7 / §5.8 门禁），换运行时版本不需要重编译引导件；**不**依赖运行时内部结构、不依赖 `process.execPath`（基线设备为 `/system/bin/appspawn`，规划 §D.8）。
9. **替代库的 SONAME 风险**：锁文件记录运行时的 SONAME 为 `libnode.so.137`，但投放名为 `libnode.so` ⇒ 按路径加载可行，但**若第三方原生扩展声明 `DT_NEEDED=libnode.so.137` 则解析失败**（规划 R18 / P0-11 ⬜ 未验）→ 本模块必须为「按库名解析」保留兜底候选（FR-002-010）。
10. **构建基线与设备基线是两个数**（TECH §5 #1）：工程 `targetSdkVersion 6.1.1(24)` / `compatibleSdkVersion 5.0.5(17)`；真机基线 `API 26 / arm64-v8a`；仅支持 `arm64-v8a`（`abiFilters`）。
