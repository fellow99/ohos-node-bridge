## 1. 项目概述

### 1.1 一句话定义

`ohos-node-bridge` 是一个 **ArkTS 组件库**：它把 Node.js 运行时（`libnode.so`）以 `dlopen` + `node::Start`
的方式在**宿主应用自己的进程里**拉起，跑在一条**独立的 detached 线程**上，并把「启动 / 观测 / 载荷 / 环境 /
宿主能力 / 关停」六件事收敛成一套 ArkTS API 与一套 Node 侧契约，让应用开发者**不必触碰** C++、ELF 属性、
seccomp、SIGSYS、字符集与线程模型。

### 1.2 关键结论速览

| 维度 | 结论 | 出处 |
|---|---|---|
| 可行性 | **可行**：已有第三方一手真机记录证明「Node 在 App 进程内成功运行 + 端上 HTTP 服务被 ArkWeb 加载」 | 🔶 notes §9 / §1.1 |
| 运行时形态 | **进程内 `dlopen` + `node::Start`**，不 spawn、不子进程、不做守护 | §4.6 路线 A |
| 渲染形态 | 由**宿主应用**自选（推荐 ArkWeb 加载本库提供的本地 HTTP 服务）；本库**不碰渲染** | §6.1 |
| JIT | **按路线 J 实施**：在册消费方的负载（Next 的 WASM SWC、`fetch` 的 undici llhttp WASM）依赖 WebAssembly。`ALLOW_WRITABLE_CODE_MEMORY` 是本形态的**App 必备 ACL**，**视为可得**（既有项目均已获批）；✅ 真机已坐实「无 ACL 即 SIGTRAP、开放权限不能替代」（§D.8），故该 ACL 属**刚性前置**而非可选项 | §4.7 + §D.8 + §9.4 |
| 原生模块移植量 | **0**：`--expose-internals` + ~20 行纯 JS 桩可替代原生 `require-builtin`（🔶 13/13 实测通过） | §4.2 ⑥ |
| libnode 来源与供给 | **选定** `electerm/ohos-node-shared` v24.2.0 的 `libnode-arm64.so`（Node 24.2.0 / 真共享库 / 七项 ELF 门禁）；**供给方式**：`runtime.lock.json` 入库（版本 + SHA-256 + 门禁 + 真机验证）、**二进制不入库**、由 `tools/provision.mjs` 从本地运行时目录（`<父工程>/ohos-node-runtime/`）幂等投放，可 `--download` 兜底；**自建延后**（路线 C） | §5.8 / 附录 D / 附录 G |
| 载荷 | **首选「只读直读、零解压」**（从安装目录直读）；仅当载荷必须可写时才退到「单个 `tar.gz` + **Node 自己解包**（谁写谁读）」 | §5.5 / §5.10 ⑩ |
| 宿主能力桥 | 库自带 **Node ↔ ArkTS 双向桥**（JSON + 线程安全），替代旧壳的 `systemPreferences.callArkTSFunction` | §5.4 |
| 包体（库侧增量） | `libnode.so` 压后 **≈43 MB**（🔶 实测）+ 引导件 14 KB；**应用载荷体积是另一笔账**（消费方文档 §7） | §5.9 / 附录 C |
| 在册消费方 | **Pi Desktop V2**：`pi-desktop-ark` / `org.fellow99.pi.PiDesktopArk`，一次性退役 Electron；其**完整规划**见其 `docs/000-工程规划.md` | §6 |
| 上架合规（库侧） | 本库的存在**不引入**浏览器内核；主 UI 由宿主的 ArkWeb 渲染（§4.8） | §4.8 |

## 2. 背景与问题陈述

### 2.1 动机：为什么需要「进程内 Node 运行时」

消费方（`pi-desktop-ark` / Pi Desktop V2）建立在**旧壳 `pi-desktop-hos`**（Electron-on-鸿蒙）之上。旧壳在真机上功能完整，
但有两个结构性问题：① **上架合规（刚性）** —— 同型工程被 AppGallery 以「渲染打开网页时未使用 ArkWeb 组件」**P0 驳回**；
② **包内浏览器内核** —— `libelectron.so` 单件 **181 MB**（✅ 实测），签名 HAP 320.3 MB（🔶 旧壳文档），
换来的只是「渲染一个本地页面」。

⇒ 新形态必须同时做到「**无 Chromium**」与「**主 UI 走 ArkWeb**」。而 ArkWeb 只能加载 HTTP(S) 页面，于是问题变成：
**在没有 Electron、也没有可用子进程（§4.4/§4.5）的前提下，如何把真正的 Node 塞进应用自己的进程**。本库就是这道题的答案。
**旧壳资产/负债的逐行盘点与迁移清单属消费方规划**（其文档 §2）。

### 2.2 本库与旧壳的本质差别

| 维度 | 旧壳（Electron on 鸿蒙） | 本库（`ohos-node-bridge`） |
|---|---|---|
| Node 载体 | Electron 主进程内置 Node（随 `libelectron.so` 分发） | 宿主进程内 `dlopen(libnode.so)` + `node::Start`（§4.6 路线 A） |
| 与 UI 的关系 | 同一个进程兼管窗口与渲染（Chromium） | **完全不碰渲染**；只负责「本地服务在端上跑着」 |
| 能力面 | Electron 全家桶（`app`/`BrowserWindow`/`session`/`shell`/…） | 六个 API 面：启动 / 观测 / 载荷 / 环境 / 宿主桥 / 关停（§5.3） |
| 体积（库侧） | 181 MB 内核 + 全部 Electron API | `libnode.so` ≈43 MB（压后）+ 引导件 **14 KB**（附录 C） |
| 升级面 | 受 Electron 版本牵引 | 只受 `libnode.so` 版本矩阵牵引（`runtime.lock.json` + 附录 G） |

### 2.3 一手事实来源：[`harmonyos-node-notes`](https://github.com/lzzhij/harmonyos-node-notes)

本工程的**全部平台结论**建立在该项目的一手真机记录上（🔶 沿用；原文路径在本地
`d:\GitHub\ohos\harmonyos-node-notes\`）。它的证据强度很高：端上 `{"node":"v24.2.0","platform":"openharmony",
"arch":"arm64"}`、`hdc fport` + `curl` 端到端、ArkWeb 真机渲染、HAP 71.8 MB *（签名产物，zip 中央目录实测）*，
并且**把失败结论一起记**（`801` / `9800005` / `9900002` 均有设备返回原文）。

**六条硬约束**（违反其一 = 崩溃或静默失败，不是报错）：

| # | 约束 | 违反后的症状 |
|---|---|---|
| ① | `libnode.so` 必须是**真共享库**（`ET_DYN` 且 **无 `PT_INTERP`**） | `dlopen` 成功，但 V8 在 `Isolate::Initialize` 第一次堆分配崩（TLS 别名） |
| ② | `libc++_shared.so` 必须一起进 HAP | `dlopen` 失败，**ArkTS 侧只拿到 `undefined`**（不报错） |
| ③ | `argc` **不能**把 `argv` 末尾的 `nullptr` 哨兵算进去 | Node 拿到 `NULL` 参数，**5 ms 内段错误** |
| ④ | JS 载荷走 `rawfile` + `resourceManager`，且**谁写谁读** | 解包出来的文件 `MODULE_NOT_FOUND`（`requireStack: []`） |
| ⑤ | `--expose-internals` 必须出现在**启动参数**里（`process.execArgv` 启动即固定） | `internal/modules/*` 全部 `MODULE_NOT_FOUND` |
| ⑥ | 同进程内 `node::Start` **只能调用一次** | 第二次命中 `node.cc` 断言 `limit_called.exchange(true)` |

**另外 5 个坑**：`--jitless`（V8 的 `PROT_EXEC` 被 W^X 拒 → SIGTRAP `Check failed: 12 == (*__errno_location())`）·
`io_uring_setup(425)` 被 seccomp trap（需 SIGSYS shim 返回**正好 `-1`** + `UV_USE_IO_URING=0`）·
UI 线程做 `dlopen` → `APP_INPUT_BLOCK`（须 detached 线程）· 商用机对 ELF 做 `.codesign` 校验 ·
`compressNativeLibs` 必须写在 `module.json5` 的 **module 级**（HAP 151.6 → 71.8 MB）。

**观测通道**（四条，缺一不可）：`snapshot_display` 截图 · `uitest uiInput` 点按 · `hdc rport` + 端上 POST 回传日志 ·
`hdc fport` + `curl` 端到端。以及三个**假信号**：hilog 里没有日志 ≠ 没执行 · `VmSize` 大 ≠ V8 起来了
（ArkTS/ArkWeb 自占约 40 GB 虚拟地址空间）· 点击「看起来生效」≠ 生效（判据是前后两次 `dumpLayout` 的差异）。

### 2.4 首个在册负载对运行时的硬要求（摘要）

本库的**第一个真实负载**是消费方的 `pi-web`（Next.js 16 服务端 + pi agent）。它的要求反过来定义了运行时
必须提供什么 —— **逐条证据与体积账在消费方文档 §2.3 / §7**，这里只留本库必须满足的**硬约束**：

| 要求（来源：消费方载荷） | 对本库的含义 |
|---|---|
| Node **`>=22.19.0`** | 选定的 `libnode.so` 必须 ≥22.19（当前 v24.2.0 ✅） |
| Next 16.3.8 **非 standalone**、进程内起服务、需要**可写** `node_modules` | 载荷形态必须支持「只读直读 + 可写缓存外置」（§5.5 路线 ①）或「自解包到可写目录」（路线 ②） |
| 设备侧 SWC 只能用 **WASM 版**；`fetch` = undici（llhttp 亦为 WASM） | **JIT 是硬前置**（§4.7）；`--jitless` 不能作为产品路径 |
| 服务端编译产物大量引用 `child_process` | 运行时必须**如实上报** `spawn` 能力（✅ 本机完整可用，§D.8） |
| `worker_threads`（图片缩放 / codemode QuickJS） | 多线程必须可用；本库不额外隔离（O3） |
| 载荷 **≈27.2k 文件 / 884 MB**（压后 156.6 MB） | 就绪幂等判据必须存在（§5.5）；首启代价要可观测（§5.7） |

## 3. 目标与原则

### 3.1 目标

1. **能起**：宿主应用在自己的进程里把 Node 拉起来，`process.platform === 'openharmony'`、`process.arch === 'arm64'`，
   `process.version` 符合库的版本矩阵。
2. **能观测**：ArkTS 侧能拿到状态机、结构化日志环、上一次崩溃记录；宿主能一条命令验「服务真的在端上跑」。
3. **能承载**：一份载荷（只读直读或 `tar.gz`）+ 入口脚本 + 环境变量 + argv，就能跑起一个真实服务端（首个在册负载 = 消费方的 `pi-web`/Next）。
4. **能对话**：Node 侧可以用一个稳定的 API 调回 ArkTS 侧的宿主能力（权限查询、目录选择、外链、通知）。
5. **能上架**（库侧）：不引入 Chromium/浏览器语义；ELF 合规；体积可控；第三方许可齐备。
6. **能发布**：`@fellow99/node-bridge` 以 HAR + 工具链的形式发布到 ohpm，接入方式可文档化、可复现。
7. **失败可见**：任何一步失败都在 UI 上留下**可截图**的文字，而不是白屏或静默。

### 3.2 设计原则

| 原则 | 展开 |
|---|---|
| **库/壳分离** | 库只负责「在进程内跑 Node」；一切应用语义（窗口、ArkWeb、鉴权、pi）留在消费方。库的 API 面越小越稳。 |
| **不隐藏平台真相** | 平台能力缺口（无 PTY、无 git、`flock` 缺失、后台不可常驻）由库**如实上报**为能力标志，绝不静默降级。 |
| **让最终使用者去读** | 凡「写入成功」的判据，一律改为「最终使用者读一遍」（🔶 谁写谁读）。 |
| **启动参数不可事后修改** | `execArgv` 只能在 `node::Start` 之前定；库把它做成显式选项，不允许运行时 push。 |
| **单例与不可重启** | 进程内只有一个运行时实例；「重启」在语义上不可实现 → 暴露成显式的失败态，而不是假装的恢复。 |
| **诊断优先于修码** | 先建观测通道（截图 / 回传日志 / `fport`+`curl` / CDP），再动代码。 |
| **零上游补丁优先** | 与旧壳同一纪律：能用现成机制（扩展、环境变量、同名顶替）就不用补丁；补丁必须幂等、可反向。 |

### 4.2 A 类：可依赖（已被真机证实）

① **进程内 `dlopen` + `node::Start`** —— 唯一可行的形态（子进程与「塞 node 可执行文件进 HAP 再 spawn」都被封死）。
② **detached bootstrap 线程** —— 必须在非 UI 线程做 `dlopen`/`node::Start`，否则 `APP_INPUT_BLOCK`。
③ **SIGSYS shim 是必需项** —— libuv 初始化会无条件探测 `io_uring_setup(425)`，shim 必须返回**正好 `-1`**；⚠️ `UV_USE_IO_URING=0` 在部分 libuv build 里**不生效**（getenv 被优化掉），设了无害但**不能当唯一手段**（§5.10 第 4 条）。
④ **载荷**：首选**放 `resfile/` 只读直读、零解压**（同形态先例在售做法）；若必须可写，则打成单个 `tar.gz` 且**由 Node 自己解包**（`zlib` + `fs`）—— **禁用**任何 OHOS 侧解压器写业务文件。
⑤ **`--expose-internals` + 约 20 行纯 JS 桩** —— 替代原生 `require-builtin`，**零原生移植**。
⑥ **`HOME` 重定向到沙箱** —— `os.homedir()` 默认指向 `/storage/Users/currentUser`（沙箱外，`EPERM`）。
⑦ **`compressNativeLibs` + `extractNativeLibs`（module 级）** —— 已验证「压缩后安装，`dlopen` 照常工作」。

### 4.5 ⚠️ 专项：`spawn` 外部程序的两份互斥证据

| 材料 | 观测 | 结论 |
|---|---|---|
| 🔶 notes §4 / §三 | `spawnSync('/bin/sh',['-c','echo x'])` → `EACCES`（而 `/bin/sh` 与 `/system/bin/sh` **都存在**） | seccomp 禁止 app 执行外部程序 |
| 🔶 旧壳 `R14`（同族设备 HAD-W32 / API 26） | `spawn('/bin/sh',['-c',…])` **能执行**且 stdout 正常（`uid=20020213 … context=u:r:debug_hap:s0`），但 **1.5 s 内变僵尸且 `exit`/`close` 永不送达**，`spawnSync` 会把主进程挂死 | 能执行，**事件语义不可用** |

**v0.5 新增（本机一手实测，HAD-W32 / HarmonyOS 6.1 / API 26，App 域）**：
`spawn('/system/bin/sh',['-c','echo SPAWN_OK; id'])` —— **完全可用且事件语义完整**：
`pid=51988`、stdout 收到 `SPAWN_OK` 与 `uid=20020219(pci) … context=u:r:debug_hap:s0`、
**`data`/`exit`/`close` 三个事件全部送达**、8 秒后 `killedAfterTimeout=false`（无僵尸）。
⇒ **本机结论：既不是 notes 的 `spawnSync → EACCES`，也不是旧壳 R14 的「事件永不送达」**。
**影响**：`bash` 工具的「stdout 随机哨兵行」workaround **不是必需**（仍可作防御保留）；
`MCP stdio` 服务器、`git` 类子进程能力、`process.execPath` 相关路径**值得重新评估**（原判「不可用」是因旧壳 R14）。

**处置（原计划，保留）**：不并入任何一侧结论，列为 **P0-4 探针**（判据：`spawn` 是否返回成功 + stdout 是否到达 + 1.5 s/15 s 后
`/proc/<pid>/stat` 是否为 `Z` + 是否收到 `exit`/`close`）。**无论哪一侧成立**，本库与消费方的设计都不依赖
`spawn` 的完成事件（`bash` 用**同名扩展 + stdout 随机哨兵行**判定结束，这是旧壳真机验证过的做法）。
> **归属**：`spawn` 的**产品用途**（`bash` 工具、`MCP stdio`、`git` 类能力）属**消费方**；本库只把它当**平台能力标志**如实上报（§3.2「不隐藏平台真相」）。

### 4.7 关键前提链：JIT ↔ ACL ↔ WASM（本工程原创结论）

```
       ┌─ Next 的 SWC 在设备侧只有 WASM 版（✅ 产物实测：next/wasm/@next/swc-wasm-nodejs） ─┐
负载依赖 WebAssembly ─┤                                                                  ├─→ 必须有 JIT
       └─ 服务端 fetch = undici，其 llhttp 解析器是 WASM（✅ pi-web 源码/依赖） ──────────┘
                                                                                              │
React 依赖：--jitless 会**关闭 WebAssembly**（🔶 notes 实测并明确警告） ─────────────────────────┘
                                                                                              │
结论：**`--jitless` 不是本工程可用的降级路径** —— 用了它 Next 起不来、`fetch` 也用不了 ────────┘
                                                                                              │
⇒ `ALLOW_WRITABLE_CODE_MEMORY`（受限权限，`system_basic` / API 14+ / 仅平板+2in1）→ **关键路径** ─┘
```

**为什么这条是本库最重要的一条判断**：notes 给的「无 JIT 就加 `--jitless`」在**它的负载**上成立
（它的主机只用 `node:http`，原生 llhttp，看不出差别），但**在首个在册消费方的负载上会把功能直接废掉**（其载荷含运行期 WASM）。因此：
- P0-1 探针必须**同时测三条**：(a) 不带 `--jitless` 是否 SIGTRAP；(b) 只声明开放权限
  （尤其 `ohos.permission.kernel.EXEMPT_ANONYMOUS_EXECUTABLE_MEMORY`，旧壳把它加进了
  `web_engine/module.json5`）时 JIT 是否可用；(c) 带 `--jitless` 时 WASM/SWC/`fetch` 是否确实全废（用来**证明**
  这条链条，而不是相信推断）。
- P0-1 探针必须**同时测三条**：(a) 不带 `--jitless` 是否 SIGTRAP；(b) 只声明开放权限
  （尤其 `ohos.permission.kernel.EXEMPT_ANONYMOUS_EXECUTABLE_MEMORY`，旧壳把它加进了
  `web_engine/module.json5`）时 JIT 是否可用；(c) 带 `--jitless` 时 WASM/`fetch` 是否确实全废（用来**证明**
  这条链条，而不是相信推断）。
- ACL 工单**与 Phase 0 并行开工**（审核约 3 个工作日；单批 ≤30 项；上一批未审完不能提新批；可用**试用调试
  Profile** 先做可行性验证）。**申报主体是宿主应用**：包名换了就必须按新包名重新申请（本库只负责在
  `module.json5` 里成对声明；申报正文见消费方文档 §10.2）。

**v0.2 追加（同形态第三方先例的实测口径）**：[`electerm/electerm-harmony`](https://github.com/electerm/electerm-harmony) 是**同一形态**的在售应用
（ArkWeb 主 UI + 进程内 `dlopen` Node + `127.0.0.1` HTTP/WS，**无 Chromium**），它的取舍给出两条路线的**真实分岔**（详见 §5.10 与附录 D）：

| 路线 | 形态 | 代价 | 判断 |
|---|---|---|---|
| **J（JIT）** | 申请 `ALLOW_WRITABLE_CODE_MEMORY`，**不加** `--jitless`；WASM 可用、性能正常 | **视为可得**：该 ACL 在本形态属 App 必备项，既有项目均已获批（申报与 Profile 见 §9.4 + 消费方文档 §10）；申报是**流程项**，不是技术未知 | ✅ **唯一主线**（唯一能直接跑消费方载荷的路线） |
| **I（解释器）** | 走 `--jitless` + 不申请任何受限权限（electerm 就是这样，**真机在售**；**本机已跑通** §D.8） | **WebAssembly 全废** ⇒ 必须把载荷改造成「零运行期 WASM」（改造项属**消费方载荷**，见其文档 §12）。**性能代价已量化**：热循环稳态 **约 9× 慢** | ⬜ **触发式备选**：**仅在 ACL 审批意外被拒/长时间未批时启动**，默认**不投入** |
| **J′（自签模板 + RX 翻转）** | 不申请 ACL，用「预签名 ELF 模板 + `dlopen` 建合法 RX 映射 + `mremap` 搬回原位」绕过 XPM 的 `PROT_EXEC` 拒绝（机制与实测数据见附录 D §D.4） | 实现成本高（需 interpose `mmap`/`mprotect` + SIGSEGV 翻转 + 模板池 + 进程内自签）；⚠️ **属对平台代码签名控制的绕行**，**不得进入上架包** | ⚠️ **技术兜底**：仅当 ACL 明确不获批**且**产品无法接受路线 I 时才立项（P0-15） |

> **准确表述**：electerm 的成功**不能**证明 `--jitless` 对首个在册消费方的负载可用 —— 它的服务端是**构建期 esbuild 打成单文件**
> （`app.bundle.mjs`，external 掉 `node-pty` 等），运行期**完全没有 WASM**；而消费方的负载（Next 的 WASM SWC + `fetch` 的 undici llhttp WASM）恰恰相反。
> 两条结论并不矛盾，**分岔点是「载荷是否含运行期 WASM」**。

## 5. 核心架构方案（库）

### 5.1 分层架构

```
┌─ 宿主应用（消费方，如 pi-desktop-ark / Pi Desktop V2） ────────────────────────┐
│  Ability + 窗口 + ArkWeb Web 组件 + 加载/错误页 + 目录选择器 + 外链 + 通知       │
│  Node 侧启动脚本：环境装配 → 载荷就绪 → 启动本地服务 → 就绪判定                  │
└───────────────┬───────────────────────────────────────────────────────────────┘
                │ ArkTS API（@fellow99/node-bridge）
┌───────────────┴───────────────────────────────────────────────────────────────┐
│  libnode_bridge.so（本库 NAPI 引导件，随 HAP 编译）                              │
│   ├─ ArkTS 侧：nativeModule 注册（createRuntime/start/logs/…/hostBridge）        │
│   ├─ 宿主能力桥：napi_threadsafe_function 队列（Node ⇄ ArkTS，JSON）             │
│   ├─ detached bootstrap 线程：dlopen → dlsym → node::Start(argc, argv)          │
│   ├─ SIGSYS shim（io_uring_setup → -1）+ setenv(UV_USE_IO_URING=0)              │
│   ├─ 崩溃处理器（hilog + 崩溃记录文件）                                          │
│   └─ stdout/stderr 重定向 → 日志环 + hilog                                       │
└───────────────┬───────────────────────────────────────────────────────────────┘
                │ dlopen
┌───────────────┴───────────────────────────────────────────────────────────────┐
│  HAP libs/arm64-v8a/：libnode.so + libc++_shared.so + libnode_bridge.so          │
│  resfile/rawfile：宿主载荷（消费方提供）+ bootstrap.js                            │
└───────────────┬───────────────────────────────────────────────────────────────┘
                │ 沙箱可写目录 <filesDir>/node-bridge/
┌───────────────┴───────────────────────────────────────────────────────────────┐
│  Node 运行时（libuv 事件循环，自己的 pthread）                                   │
│   bootstrap.js：可选自解包（zlib+fs）→ 解析入口 → require/import → 应用逻辑      │
│   宿主桥：require('@fellow99/node-bridge/host').invoke('perm.check', …)          │
└───────────────────────────────────────────────────────────────────────────────┘
```

**一条关键边界**：库**不参与**渲染。ArkWeb 页面、加载页、错误页都是消费方的事；库只保证「本地服务在端上跑着」。

### 5.2 线程与生命周期模型

| 项 | 设计 | 依据 |
|---|---|---|
| 启动线程 | `std::thread(...).detach()` 一条**专用 pthread** 做 `dlopen` + `dlsym` + `node::Start` | 🔶 UI 线程做会 `APP_INPUT_BLOCK` |
| 线程与 ArkTS 线程的关系 | 两者**完全解耦**：ArkTS 只做「投递启动参数 + 查状态 + 读日志」，绝不 join | `node::Start` 直到进程结束才返回 |
| 单例 | **进程内单例**：`NodeRuntime.instance`；`start()` 只允许一次；二次调用抛错并保留首次失败原因 | 🔶 硬约束 ⑥ |
| 状态机 | `idle → starting → running → (failed) → stopping → stopped`；`failed` 携带 `stage` + 原始错误/信号 | 失败可见 |
| 失败后的恢复 | **不假装恢复**：`failed` 后只允许「读日志 / 读上次崩溃记录 / 提示重启应用」 | 硬约束 ⑥ |
| 关停 | `shutdown()` = 在 Node 线程执行应用注册的 `onShutdown` 钩子（如 `server.close()`），并等待窗口期；**真正的停止只能是进程退出**（消费方在 `onPrepareToTerminate` 里调用） | 旧壳 `before-quit` 语义的等价物；`PREPARE_APP_TERMINATE` 权限已在旧壳清单里 |
| 载荷解包 | 在 Node 线程内做（`bootstrap.js`），不在 UI 线程、也不在 ArkTS 侧 | 硬约束 ④ + 谁写谁读 |

### 5.3 ArkTS 对外 API（草案）

```ts
// @fellow99/node-bridge —— ArkTS（.ets / .d.ts 同形）
export type NodeRuntimeState = 'idle'|'starting'|'running'|'failed'|'stopping'|'stopped';

export interface NodeRuntimeOptions {
  entry: string;                 // 入口 JS：相对 payloadRoot 的路径，或绝对路径
  payloadRoot?: string;          // Node 可写根；默认 <filesDir>/node-bridge/payload
  archive?: string;              // 载荷 tar.gz：arkts 资源名（rawfile）或真实路径；给出即自解包
  archiveSha256?: string;        // 幂等 marker 的判据（缺省则由库计算一次并落盘记下）
  argv?: string[];               // 传给 Node 的 argv（默认 [ 'node', <entry abs> ]）
  execArgv?: string[];           // 默认 ['--expose-internals','--no-verify-heap']
  env?: Record<string,string>;   // 合并进进程环境（HOME/TMPDIR/PI_* / NO_PROXY …）
  cwd?: string;                  // 默认 payloadRoot
  capBytes?: number;             // 单次 JSON 载荷上限（默认 8 MiB，见 §5.4）
  logRingSize?: number;          // 日志环容量，默认 500 行
  jitless?: boolean;             // 诊断专用；默认 false（用了就等于关闭 WASM，见 §4.7）
  onLog?: (e: NodeLogEntry) => void;
  onStateChange?: (s: NodeRuntimeState, detail?: string) => void;
}

export interface NodeLogEntry { at: number; stream: 'stdout'|'stderr'|'system'; text: string; }
export interface CrashRecord { at: number; stage: string; signal?: string; hint?: string; logTail: string[]; }

export declare class NodeRuntime {
  static readonly instance: NodeRuntime;               // 进程内唯一
  readonly state: NodeRuntimeState;
  readonly pid: number;                                 // = 宿主进程 pid（不是子进程）
  start(opts: NodeRuntimeOptions): Promise<void>;       // 立即返回；解析到 starting
  waitUntilRunning(timeoutMs?: number): Promise<void>;  // 轮询状态，不阻塞 UI
  logs(): NodeLogEntry[];
  lastCrash(): CrashRecord | null;                      // 上次运行留下的崩溃记录
  shutdown(reason: string): Promise<void>;              // 触发 Node 侧 onShutdown 钩子
  readonly host: NodeHostBridge;                        // 宿主能力桥（Node → ArkTS）
}

export declare class NodeHostBridge {
  /** 注册一个宿主能力处理器；handler 在 ArkTS 主线程被调用，入参/出参都是 JSON 字符串 */
  register(name: string, handler: (payloadJson: string) => string | Promise<string>): void;
  unregister(name: string): void;
  list(): string[];                                     // 供日志与自检
}
```

Node 侧（由 `libnode_bridge.so` 提供的**内置模块**，无需 npm 安装）：

```js
const host = require('@fellow99/node-bridge/host');    // 由 process.dlopen 暴露的 builtin
const facts = await host.invoke('runtime.facts');       // { node, platform, arch, execArgv, state }
host.handle('shutdown', () => new Promise(r => server.close(r)));   // 注册 Node 侧钩子
```

> **与旧壳的对照**：旧壳用运行时的 `electron.systemPreferences.callArkTSFunction`（≤3 参、仅原始类型）。
> 本库自建同型能力，但用 **JSON 字符串**做载体（不受参数个数与类型限制），并**明确超时**（默认 10 s）。
> 🔶 notes 的警告照抄进设计纪律：**异步方法必须走异步入口**，否则会永久阻塞 Node 线程。

### 5.4 宿主能力桥（Node → ArkTS）

| 项 | 设计 |
|---|---|
| 方向 1（Node → ArkTS） | Node 线程 `host.invoke(name, json)` → 入队 → ArkTS 主线程执行 handler → 结果回投 → Node 侧 Promise resolve。**Node 线程不阻塞在 ArkTS 上**（除非调用方显式要求同步，且带超时） |
| 方向 2（ArkTS → Node） | 只有两条：`start()` 的启动参数、`shutdown()`。不提供「ArkTS 调 Node 函数」的通用入口（保持 API 面小；应用语义走 HTTP/文件） |
| 线程安全 | 用 `napi_threadsafe_function`（在 ArkTS 侧创建，回调在 ArkTS 线程执行）；队列有界，溢出即报错而非静默丢弃 |
| 能力清单（v1） | `runtime.facts` · `perm.check`（对齐旧壳 `checkPermission`）· `perm.openAppInfo`（对齐 `openApplicationInfoEntry`）· `fs.pickFiles` / `fs.pickFolder`（系统选择器 → 沙箱路径）· `shell.openExternal` · `notify.show` · `log.hilog`（关键信息必须同时进 hilog） |
| 失败语义 | 未注册的名字 → 明确 reject（**不允许**静默返回空）。**反面教材**：旧壳的 `ExternalWeb.Open` 从未注册，调用点直接解引用空指针把整个应用打崩（🔶 `R15`），本库必须**注册表校验 + 报错**而不是崩溃 |
| 参数上限 | JSON 载荷单次 ≤ `capBytes`（默认 8 MiB，可配）；选择器返回的文件**只回传沙箱内路径**，不回传内容（大文件走 copy） |

### 5.6 环境契约

| 变量 | 值 | 谁设 | 理由 |
|---|---|---|---|
| `HOME` / `USERPROFILE` | 宿主可写沙箱（`<filesDir>`） | **库**（默认）| 🔶 `os.homedir()` 指向沙箱外 → 文件选择器 `EPERM` |

| `NODE_OPTIONS` | **清空**（构建/运行期都清） | **库** | 旧壳构建期 `build-hap.ps1:142-143` 已这么做；避免宿主环境污染 |

### 5.7 日志与崩溃取证

| 通道 | 设计 |
|---|---|
| stdout/stderr | C++ 侧 pipe 重定向 → 逐行入**有界日志环**（默认 500 行）+ **同时打 hilog**（🔶「应用侧 INFO 常不进 hilog dump 缓冲」⇒ 级别要选能进缓冲的） |
| ArkTS 读取 | `logs()`；消费方把它渲染到「开发者/诊断」面板（**把界面当调试台**：一张截图胜过十次盲猜） |
| 崩溃记录 | 崩溃处理器（信号 + `backtrace`）写 `<filesDir>/node-bridge/last-crash.json` + hilog；下次启动 `lastCrash()` 可读 |
| 端到端证书 | 库自带 `selfcheck` 载荷：起 `node:http` 服务并暴露 `/facts`（`{node, platform, arch, execArgv, hostBridge, state}`），供 `hdc fport` + `curl` 验证 —— **这条 JSON 就是一次真机成功运行的证书**（🔶 notes 通道 ④） |
| 调试通道 | debug 构建才允许 `--inspect`（`hdc fport tcp:9229 tcp:9229` + DevTools 连 Node）；ArkWeb 侧用其自身调试开关；**release 必须关闭**（旧壳 `R7`：`--inspect` 默认开启等于把宿主交出去） |
| 禁止的判据 | 不用 hilog「有没有那行」判执行；不用 `VmSize` 判 V8 是否起来；不用「点击看起来生效」判 UI（用前后两次 `dumpLayout` 差异） |

### 5.8 运行时的获取、校验与（未来）自建

| 项 | 设计 |
|---|---|
| 获取与投放 | `node tools/provision.mjs --out <模块>/entry/libs/arm64-v8a`（**幂等**；`--check` 只校验 / `--list` 打印锁定项）。来源优先级：**本地运行时目录** `<父工程>/ohos-node-runtime/`（可用 `OHOS_NODE_RUNTIME_DIR` 覆盖）→ `--from <path\|url>` → `--download`（镜像 → 上游）；完整设计见 **附录 G** |

| 校验（**七项，任一不过即硬失败**） | ① `e_type = ET_DYN`；② **`PT_INTERP` 计数 = 0**（PIE 直接拒）；③ `e_machine = AArch64`；④ `DT_NEEDED` 含 `libc++_shared.so`；⑤ `node::Start`（`_ZN4node5StartEiPPc`）在 `.dynsym` 中**已定义且导出**；⑥ SHA-256 与锁文件一致；⑦ 大小与锁文件一致**且**版本串存在。已实现于 `tools/provision.mjs`（纯 JS 自解析 ELF，不依赖 python/llvm） |
| 签名标记与自签 | **HAP 内原生库不需要 `.codesign`**（§D.6 + §D.9 复验：无签名段的 `libnode.so` 在真机 `dlopen` 成功、`hilog` 无 `xpm`/`unsigned file`）⇒ **R22 关闭**。`--sign` 只服务「**脱离 HAP 独立分发**」：`ohos-selfsign.mjs` 做 `add-section` + `sign`，**不需要私钥/证书**（纯 SHA-256 Merkle + fs-verity descriptor，算法见 §D.4）；中间产物落系统临时目录，**必须在 strip 之后** |
| 自建（**延后**，2026-10-16 决策） | 配方已归档在 **附录 D**（`--openssl-no-asm --shared`、条件 `--v8-disable-temporal-support`、**V8 `maglev-assembler.h` release 补丁 + `-DNDEBUG`**、版本补丁 `0001`/`0002`/`-Wno-error=implicit-function-declaration`、`CC/CXX` 带 `-fno-emulated-tls`，随后 `llvm-strip` → 自签）。**只在需要非 v24.2.0 版本 / 供应链必须自控时启用**（附录 G.6 路线 C） |
| 为什么先用现成产物 | 自建是数小时级构建 + 供应链可控的长期方案，但**不该阻塞链路可行性**；库只依赖 ELF 属性与 `Start` 符号，产物可随时替换（升级路径见附录 G.6） |
| 供应链纪律 | 锁定来源 + SHA-256 + 归档构建配方与许可清单；**不引入无法复现的黑盒二进制**（风险 R8）；每条记录带 `verifiedOn`/`verifiedDevice`/`verifiedNotes`，把「验过没有」写进文件 |

| # | 要点 | 为什么（不做会怎样） |
|---|---|---|
| 1 | `dlopen` + `node::Start` 在 **detached pthread（32 MB 栈）**里做 | 在 UI 线程做会 `APP_INPUT_BLOCK`；先例的旧版本就因此被系统 ANR 杀掉 |
| 2 | **SIGSYS handler 内禁止 `printf`/`vsnprintf`/`OH_LOG_Print`**，只能手写数字 + 裸 `write(2)` | 信号上下文里调 stdio 会二次崩溃；本库的 hilog 输出必须放到 handler **之外** |
| 3 | 判断「是否跳过 `svc` 指令」必须**读指令编码**（`0xd4000001`），不能用 PC 与 `si_addr` 比较 | 后者在部分设备上恒不相等 ⇒ shim 静默失效 |
| 4 | shim 返回**精确 `-1`**；`UV_USE_IO_URING=0` 在该 libuv build 里**不生效** | 返回 `-ENOSYS`/`-38` → libuv `uv__close(-38)` 触发 `assert(fd > STDERR_FILENO)`，仍崩 |
| 5 | **stdio 必须重建并持续排空**：`fd0=/dev/null`、`fd1/2` 接 1 MB pipe + 独立 reader 线程 | 不排空管线会**阻塞 ArkWeb 的 IO 线程** ⇒ 「Web 组件不绘制」（最难查的一类白屏，登记 R19） |
| 6 | ArkWeb 侧：`Web({src: $rawfile('loading.html')})` → **HTTP 探活（退避重试）** → `loadUrl('http://127.0.0.1:<port>/')` | ✅ 证明 **ArkWeb 渲染进程能访问 `127.0.0.1`**（消费方文档 §6.2 路线 ① 的第三方证据），且**页面由本地服务渲染 ⇒ 天然同源、零 CORS** |
| 7 | 只开 `javaScriptAccess(true)` + **`domStorageAccess(true)`**；先例未开 `databaseAccess` | `domStorageAccess` 缺失 ⇒ `localStorage = null` ⇒ SPA 首屏崩；是否需要 `databaseAccess` 由本工程 P0-3 判 |
| 8 | 加载页必须是**应用内资源页**；起来后 `clearHistory()` 并在 `onBackPress` 守卫 | 不清历史 ⇒ 返回键/手势把用户永久卡在「Starting engine…」 |
| 9 | 外链用 `onLoadIntercept` + **`isMainFrame()`**（子 frame 放行），或直接交系统浏览器 | 等价于旧壳的 `setWindowOpenHandler` + `will-navigate` |
| 10 | **载荷零解压**：应用载荷原样放 `resources/resfile/<app>/`，Node 从**只读安装目录**直读 | ✅ 免掉首启解压 27k 文件的耗时与失败面（§5.5 因此改为「只读直读为首选」） |
| 11 | 权限申请放在 `loadContent` **之后**；`onCreate` 里**先起 Node 再** `loadContent` | 权限弹窗在无人点按的设备上会卡启动屏 → `APP_INPUT_BLOCK` |
| 12 | 单实例 `launchType: "singleton"` + **固定端口** | 多实例会互抢端口与数据目录（先例靠单实例规避；本工程默认随机端口 + 单例） |
| 13 | 崩溃取证：信号 handler 记录 `pc/sp/lr/x0/si_addr` + `dladdr` backtrace；release **保留 native 符号**（`nativeLib.debugSymbol.strip=false`） | 进程内 Node 崩溃**无法自动重启**（硬约束 ⑥），只能靠证据定位 |
| 14 | 状态回传 `idle｜launching｜running｜failed:<detail>` 由 ArkTS 轮询，**失败立刻回退**而不是等满超时 | 把「再等等就好了」变成「立刻知道坏了」 |
| 15 | **权限面极小**：`INTERNET` + 目录权限 + 剪贴板；**没有**受限 ACL 权限、也没有 `KEEP_BACKGROUND_RUNNING` | 与 §9.4「按需最小化」一致；他们用 `--jitless` 换掉了对 JIT 权限的依赖 |
| 16 | 子进程路径**确认不可用**（先例保留为代码注释）：app 子进程里 `execve` 任何新镜像都被拒（直连 / 系统加载器 / memfd **全 EACCES**，XPM 拦 uid），且子进程 seccomp **更严** ⇒ libuv 在里面被 SIGSYS 杀 | 强化 §0.3「不做子进程」，并给 §4.5 的 P0-4 提供预期判据 |

**先例没做、但本工程必须做（差分清单）**：`--expose-internals`（内部模块桩）· **宿主能力桥**（先例只有 4 个 `javaScriptProxy` 方法）·
载荷压缩 `compressNativeLibs`（先例的 HAP 里 `libnode.so` **未压缩**）· 载荷裁剪（先例构建期 esbuild 打成单文件；宿主若要带完整 `node_modules`，裁剪策略由消费方定）
`databaseAccess` / Cookie 注入 / `--inspect` 调试通道（先例均未配置）。

**先例明确放弃的**：本地终端 / PTY（`node-pty` external + `DISABLE_LOCAL_TERMINAL=1` + `hasNodePty=false`）· 子进程兜底（保留代码但设备上不可用）· 运行期解压。

## 6. 消费方对接契约（摘要）

> **完整规划在另一份文档**：`pi-desktop-ark/docs/000-工程规划.md`（**Pi Desktop V2** / `org.fellow99.pi.PiDesktopArk`）。
> 本节只写**两边共享的接口**：库承诺什么、消费方必须自建什么、哪些事实双方都不许偏离。
> 原 §6.1–§6.7 的详细内容已整体迁出，**旧引用请按 §6.4 的映射表对照**。

**目标形态（一句话）**：应用宿主 ArkTS 起本库 → 本库在**同一进程**内跑 Node → Node 起 `pi-web` 服务端
（同源 HTTP + SSE）→ **ArkWeb** 渲染 `http://127.0.0.1:<随机端口>/`。**无 Electron、无 Chromium。**

### 6.1 承诺与责任（一分到底）

| 面 | 本库承诺 | 消费方必须自建 |
|---|---|---|
| 运行时 | `dlopen` + `node::Start`、单例状态机、启动参数、SIGSYS shim、崩溃取证、自检载荷 | 无（**不写 C++**） |
| 载荷 | `entry` / `payloadRoot` / `archive` / `cwd` / `env` 选项；就绪幂等；CJS/ESM 入口解析 | 载荷内容与裁剪、投放时机、首启加载页 |
| 观测 | 日志环 + hilog + `lastCrash()` + `/facts` 自检端点 | 诊断面板、错误页、阶段文案、真机取证 |
| 宿主能力 | 桥的**传输层**（线程安全 JSON、超时、未注册即报错） | 每个能力的**实现**（权限、选择器、外链、通知） |
| 渲染 | **不参与**（只保证「本地服务在端上跑着」） | ArkWeb `Web` 组件、加载页、Cookie 注入、导航围栏 |
| 生命周期 | `start()` / `waitUntilRunning()` / `shutdown()`（触发 Node 侧钩子） | `onPrepareToTerminate` 接线、失败态 UX |
| 平台真相 | 如实上报能力标志（**不静默降级**） | 把失败暴露到 UI（可截图、可断言） |

### 6.2 双方共享的事实（任一方改动都要同步）

| # | 事实 | 依据 |
|---|---|---|
| 1 | 监听端口由 Node 侧**随机/先探测空闲**；宿主应用必须**单实例** | ✅ §D.10 ⑰：端口冲突 ⇒ 载荷未捕获异常 ⇒ **整个 App 进程 abort** |
| 2 | 载荷必须自装 `uncaughtException` / `unhandledRejection` 兜底并写**独立日志通道** | ✅ §D.10 ⑱：`dup2` 会把宿主 Web 容器的原生输出混进 `node.log` |
| 3 | `HOME`/`TMPDIR` 由库重定向到宿主可写沙箱；应用语义变量（如 `PI_*`）由消费方经 `env` 传入 | §5.6 |
| 4 | 鉴权策略由消费方定（**首选 loopback 免密**）；库只负责「服务监听在哪里」 | 上游源码事实见 §6.3 |
| 5 | `execArgv` 只能在 `node::Start` **之前**定，运行时不可 push；`--jitless` 只用于诊断 | §5.2 / §4.7 |
| 6 | 库**不认识** `pi` / `pi-web` / `PI_WEB_PASSWORD` / Next.js | §0.3 |

### 6.3 鉴权相关的上游源码事实（消费方选型用，✅ 已逐行核实）

- `pi-web/lib/web-auth.ts:15-19`：`isWebPasswordEnabled()` = `PI_WEB_PASSWORD` 非空 ⇒ **未设密码则认证整体关闭**；
- `pi-web/lib/request-security.ts:90-102`：`isApiRequestHostAllowed()` 对 **loopback 主机名/IP 字面量直接放行**
  ⇒ 同源请求天然通过，**不需要头改写**（这也是消费方比同型工程少一套补丁的原因）；
- `pi-web/proxy.ts:42-47` / `:50-70`：未启用密码时只要过 Host 围栏即放行；启用密码后**会话 cookie 优先**
  （对 `/api/*` 同样生效），Basic 头只是**额外**一条路径。

⇒ 结论（**消费方的结论，库不实现**）：**loopback 免密为首选**；回退是「绑局域网 + 密码 + Cookie 注入」。
两条路线都**不改上游、不加 preload 桥、不引入 IPC 载体**。

### 9.4 权限

| 类别 | 项 | 说明 |
|---|---|---|
| **受限（ACL，由宿主应用按自己的包名申请）** | `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY`（`system_basic` / API 14+ / 仅平板+2in1 / `system_grant`） | **本形态的刚性前置**（V8 JIT 必需，不可删除）：无它时不带 `--jitless` 即 SIGTRAP（§D.8）；**视为可得**（既有项目均已获批）且 ✅ **已在消费方真机实证**（§D.10）。库在 `module.json5` 里把它与 `requestPermissions`/`definePermissions` 成对声明（与 `pi-desktop-hos` 逐项一致）；**申报与 Profile 由宿主应用负责** |
| 开放（免 ACL） | `INTERNET`（宿主网络）、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING`（配合 `backgroundModes`）、`PREPARE_APP_TERMINATE`（优雅关停）、`RUNNING_LOCK` 等 | 库**只声明自己需要的项**；其余由宿主按需声明（**不要照抄旧壳的 21 条**） |
| 用户授权 | `READ_PASTEBOARD`、`READ_WRITE_{DESKTOP,DOCUMENTS,DOWNLOAD}_DIRECTORY` | 由宿主应用按功能需要申请（见其 `docs/ACL配置.md`） |
| **本库不申请** | 二进制证书（`certType: 4`）、`ALLOW_EXTERNAL_NATIVE_CODE`、`kernel.LOAD_INDEPENDENT_LIBRARY`、`CUSTOM_SANDBOX`/`RUN_ANY_CODE` 等 | 理由：库不分发自有**可执行** ELF；`libnode.so` 是**库**而非独立二进制（⬜ 口径在 P0-7 与上架材料中确认） |

**ACL 提交与踩坑**（🔶 沿用 + ✅ 一次实证）：AGC → 项目设置 → **ACL 权限**页签 → 选权限 + 填申请原因（≤256 字）
与使用场景 → 审核约 3 个工作日；单次 ≤30 项；上一批未审完不能提新批；获批权限在**创建发布 Profile 时写入**，
Profile 创建后 ACL 变化**必须重建 Profile**；可用**试用调试 Profile**（5 天 / 每应用最多 5 个）先做验证。
**✅ 已踩过的坑**：声明面配好、但 **Profile 不含 ACL** 时 `hdc install` 直接被拒
（`code:9568289 / PermissionName: ohos.permission.READ_PASTEBOARD`）—— 处置与复现步骤见消费方 `docs/ACL配置.md`，
申请正文（可直接粘贴）见消费方文档 §10.2。

**v0.2 由此产生的两条硬口径**

1. **SONAME（`libnode.so.137`）与 HAP 内文件名（`libnode.so`）不一致**：
   - `dlopen("libnode.so")`（按路径）**不受影响**；
   - 但任何 Addon 若以 `DT_NEEDED = libnode.so.137` 链接，运行期会**找不到** ⇒ **桥件不得依赖 `DT_NEEDED` 指向 libnode**，
     改为依赖「libnode 以 **`RTLD_GLOBAL`** 加载 → 其符号进入全局符号表」；
   - 因此本库的 `dlopen` 标志定为 **`RTLD_NOW | RTLD_GLOBAL`**（同形态先例用的是 `RTLD_LOCAL`，因为它**没有任何 Addon** —— 我们没有这个自由，登记为 **R18**）。

## 附录 G. 运行时产物供给设计（没有制品库也能发版）

> 决策日期 2026-10-16（用户口径）：**没有可用的制品库**；运行时产物放**父工程本地目录**
> `<父工程>/ohos-node-runtime/`（与 `harmonypc-electron-versions/` 同构）；**不做 x86_64**（只用真机调试）；
> **自建配方延后**。

### G.1 两层解耦：什么进 git，什么不进

| 层 | 内容 | 进 git？ | 理由 |
|---|---|---|---|
| **锁（事实源）** | `ohos-node-bridge/runtime.lock.json`：版本、大小、SHA-256、SONAME、门禁结果、许可、出处、真机验证记录 | ✅ 进 | 几十行 JSON，无版权与体积问题；`diff` 即审计 |
| **产物（二进制）** | `libnode-arm64.so`（120.9 MiB） | ❌ **不进** | ① GitHub 单文件 **100 MiB 硬限**（用 LFS 又会把 clone 变成必须联网的重操作）；② Release/制品库更适合放"发布物"；③ 二进制进 git 会在每次换版本时留下永久历史 |
| **投放工具** | `tools/provision.mjs`（幂等 + 七项门禁） | ✅ 进 | 没有它，锁文件就只是一份文档 |
| **缓存目录** | `<父工程>/ohos-node-runtime/node-<版本>/`（本机填充） | ❌ 不进（父 `.gitignore` 已含 `/ohos-node-runtime`） | 与 `harmonypc-electron-versions/` 同一模式：本机缓存，可随时按 §G.3 重建 |

⇒ 结果是：**clone 本库能拿到「该用哪个二进制、校验值是多少、怎么投放、验过没有」**，
但**不会**把 120 MB 塞进仓库；拿不到二进制时 `provision.mjs` 给出三条明确出路（本地放置 / `--from` / `--download`），
**不会静默降级**。

### G.2 目录与命名

```
<父工程>/
├── ohos-node-runtime/                  # ← 运行时缓存（不入库）
│   ├── README.md                       # 目录约定与重新填充步骤
│   ├── SHA256SUMS                      # sha256sum -c 可直接用
│   └── node-v24.2.0/
│       ├── libnode-arm64.so            # 上游资产**原名**（不改名，便于与上游比对）
│       └── PROVENANCE.md               # 该版本溯源 + 门禁 + 真机验证
└── ohos-node-bridge/
    ├── runtime.lock.json               # ← 唯一事实源（入库）
    └── tools/provision.mjs             # ← 投放工具（入库）
```

**为什么保留上游资产原名**（`libnode-arm64.so` 而不是 `libnode.so`）：库里放的是「**某次 release 的某个资产**」，
改名后就无法自证它对应哪个 URL；部署进 HAP 时才由锁文件的 `deployAs` 统一成 `libnode.so`。

### G.3 来源优先级（`provision.mjs` 的实际行为）

| 顺序 | 来源 | 触发条件 | 说明 |
|---|---|---|---|
| 1 | 本地运行时目录 | 默认 | 路径 = `lock.localStore.path`（`../ohos-node-runtime`），可用 **`OHOS_NODE_RUNTIME_DIR`** 覆盖（CI / 另一台机器） |
| 2 | `--from <path｜url>` | 显式指定 | 内网、镜像、临时验证用 |
| 3 | `--download` | 显式指定 | 依次尝试 `mirror.url` → `source.url`；**任一失败自动尝试下一个**，全失败才报错 |
| — | 无论哪条来源 | — | 一律要过 **七项 ELF 门禁 + SHA-256 比对**；不符即 `exit 2` |

**联网时的真实坑（已实测）**：Node 内置 `fetch` **默认不读** `HTTPS_PROXY`/`HTTP_PROXY`，
国内网络必须显式开 `NODE_USE_ENV_PROXY=1`（Node ≥ 24）。`provision.mjs` 在检测到代理变量而未开该开关时，
会直接把正确命令打出来（实测：不带开关 `fetch failed` → 带开关 **8 s 下载完成且 SHA 一致**）。

### G.4 幂等与门禁（`provision.mjs` 契约）

| 行为 | 细节 |
|---|---|
| 幂等 | 目标 `libnode.so` 的 SHA-256 已等于锁值 ⇒ **跳过拷贝**（`--force` 强制）；`libc++_shared.so` 同理 |
| 硬失败 | SHA 不符、任一 ELF 门禁不过、找不到 `libc++_shared.so`、锁里没有该版本 ⇒ **`exit 2`**，绝不「就地找另一个凑合」 |
| 副作用面 | 只写 `<out>/libnode.so` 与 `<out>/libc++_shared.so`；`--sign` 的中间产物**一律落系统临时目录**（`libs/<abi>/` 里多一个文件就会被**打进 HAP**） |
| 退出清理 | 下载 / 签名的中转文件在进程退出时删除（单份可能上百 MiB） |
| 只校验 | `--check`（可进 CI）/ `--list`（打印锁定项） |
| 自签 | `--sign`：`ohos-selfsign.mjs add-section` + `sign` + `verify`；**只为独立分发准备**，HAP 内不需要（§D.6、§D.9） |

### G.5 为什么否掉另外四种做法

| 做法 | 否掉的原因 |
|---|---|
| **git submodule 指向上游构建仓库**（如 `hqzing/ohos-node`） | 上游不动二进制（无 release），拿到的只是构建脚本；且把「取产物」变成「必须联网 clone 别人的仓库」 |
| **直接 commit 二进制进本库** | 120.9 MiB > GitHub 100 MiB 单文件硬限；即便用 LFS 也要所有使用者装 LFS 才能 clone |
| **引入制品库**（Nexus / OSS / 私有 registry） | 本工程与消费方都没有现成制品库；为一枚可校验的 `.so` 引入一套服务，运维成本 > 收益（用户口径：无可用制品库） |
| **等自建产物再开工** | 自建是数小时级构建 + 供应链可控的长期方案，但**不该阻塞链路可行性**；库只依赖 ELF 属性与 `node::Start` 符号，产物可随时替换（→ §G.6） |

### G.6 演进路线（三条，按需启动，互不冲突）

| 路线 | 何时启动 | 要做的事 |
|---|---|---|
| **A. 现状（本地目录 + 锁文件）** | 默认 | 本机 / 内网跑 `provision.mjs` 投放即可，**离线可用** |
| **B. 公开镜像** | 第三方（ohpm 使用者）需要自己拿产物时 | 新建 `fellow99/ohos-node-runtime` 的 Release，资产**逐字节复制**上游 + 附 `SHA256SUMS`；回填 `lock.runtimes[].mirror`（`provision.mjs --download` 会自动优先走它）。**不做改编译**，只做「可访问的镜像」 |
| **C. 自建配方** | 需要非 v24.2.0 版本 / 供应链必须自控时 | 走**附录 D** 的配方（`--openssl-no-asm --shared`、V8 maglev release 补丁 + `-DNDEBUG`、`-fno-emulated-tls`、`llvm-strip` → 自签），配方 vendor 进 `tools/rt-build/`（**当前未落地**，本次决策延后）。自建产物同样必须先过七项门禁 + 真机探针，再进锁文件 |

### G.7 `runtime.lock.json` 字段速查

| 字段 | 含义 |
|---|---|
| `schema` | 结构版本（当前 `1`） |
| `active` | 当前选用的 `{node, abi}`；**换版本就是改这一行** |
| `runtimes[]` | 每个可用产物一条：`node` / `nodeModuleVersion` / `abi` / `file`（上游原名） / `deployAs`（HAP 内名） / `size` / `sha256` / `soname` / `needsLibcxx` / `embeds` / `flags` / `signed` / `source` / `mirror` / `gates` / `verifiedOn` / `verifiedDevice` / `verifiedNotes` |
| `libcxx` | `libc++_shared.so` 的**来源规则**（从 ohos-sdk 取 + `sdkRelPath`），**不固化哈希**——它随 SDK 版本变化 |
| `localStore` | 本地缓存目录（`path` + `envOverride` + `layout`） |
| `openItems` | 尚未闭环的事（暂无镜像 Release、自建延后、x86_64 不做）——**故意留在文件里**，让「未完成」跟着代码走 |

### G.8 与发布物的关系

**ohpm 包（HAR）里不带 `libnode.so`**：HAR 只发布 ArkTS 源码 + NAPI 引导件源码/types + `payload/` + **锁文件 + 投放工具**，
消费方在自己的构建流水线里跑一次 `provision.mjs` 投放（与旧壳从 `harmonypc-electron-versions/` 取运行时同构）。理由：
① 120 MB 二进制塞进 ohpm 包会让每个使用者都下 120 MB；② 各消费方可能需要不同版本 / 不同签名策略；
③ 二进制走 Release / 本地目录比走包管理器更合适。（§7.5 同步）
